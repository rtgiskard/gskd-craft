# 设计正反例

这些例子归纳个人判断尺度，不是当前项目的验证记录；不补造历史实现、指标或授权。下列正例是如何行动的示例，不声称当时已如此完成。项目名称、框架和具体工具都不是适用前提。

## 干净是基线，不以改动量衡量

**反例**：为让一个文件变短，把状态、更新与清理分别移到几个文件，再用转发函数连接；只用行数下降证明“更优雅”。另一种反例是借“不为行数”拒绝梳理已经割裂的责任，或只证明新条件能挡住原反例，就默认应继续沿用当前问题框架。

**正例**：先说明目标结果、真实约束及哪一个不变量或生命周期需要完整所有者，再比较迁移前后谁创建、谁更新、谁释放，以及调用者是否还必须了解同一批内部细节。例如完成回调反复为维护期间争写补条件，应检查 writer 接纳前能否建立一致基线、维护期间哪些操作仍有权产生写入，而不只补最后报错的入口。若现有边界正确、错误仅在单处换算，直接修正即可。能降低理解成本、消除重复责任的边界值得建立；纯机械搬运可以是必要步骤，但本身不是设计收益。

**落点**：责任清楚、状态语义一致是基础要求，不是用户额外要求才提供的优化；整体判断既不要求最短文件，也不默认更大重构。局部修复可以是整体判断后的最佳选择，但不能仅因改动少或原反例通过就接受。已授权重构覆盖实际调用点，不留下新旧两套路径。

## 领域主干与少量完整的连接机制

**反例**：为统一技术栈，把有独立实时约束的音频路径放进通用异步队列；或为了“运行时无关”新增可切换多种 runtime 的万能接口，让业务模块先理解调度器、线程桥接和任务句柄。

**正例**：业务主干直接表达接纳、状态转换与提交，I/O 和实时处理各守其执行边界；连接机制只承担必要的请求、结果和生命周期，不让各调用方重复补取消、等待和回收。如果完整 runtime 比小组件拼装更少胶水、更清楚，也可以选它。

**落点**：统一契约不等于统一执行方式，轻量不等于最少依赖或线程。这是按责任与约束判断表达的原则，不是某种 runtime、固定线程模型或音频架构的通用推荐；结构清楚也不证明性能更好。

## 附加品质不自动成为新目标

**反例**：用户只要求悬浮时显示音量，助手为让悬浮期间外部音量变化也实时刷新，新增 hover 状态、浮层和窗口离开清理；把现成 tooltip 的边际不足升级为新的生命周期责任。

**正例**：先判断现成机制是否满足已接受的显示与交互要求，足够就复用；如果用户明确要求连续追踪变化，再选择动态显示机制，完成相应退出与清理，不以“简单”为由降级验收。

**落点**：取舍针对新增责任所服务的目标，不是禁止自定义浮层或一律优先最低成本；已要求的品质仍须兑现。

## 面板缓存的收益不抵复杂度

**反例**：看到重复构造就加一个通用面板缓存，却不说明缓存归谁、何时失效或退出如何释放；用“以后都能复用”掩盖当前收益不足。反过来，把这次不划算变成永久禁用缓存，也超出了证据。

**正例**：先明确现有负担与无缓存基线，再问命中收益是否抵得过容量、键、失效、同步和生命周期管理。不能只说“更快”，还要说明计算代价搬到哪种资源或维护责任上。当前收益不抵复杂度就推荐保留直接构造；需求或证据改变时可以重评。

**落点**：选择由当前工作负载决定。采样、统计、视觉保真与资源对照等测量细则复用当前项目适用的验证指南；没有相应证据就明确收益待验证，不引用历史结论冒充本次结果。

## 单版实验退化，不等于方向无效

**反例**：用户要求实现异步候选并比较，助手只替换任务启动方式，用热缓存串行耗时就建议放弃异步方向；未检查调度粒度，也未观察目标关心的前台响应。另一种偏差是在视觉探索中擅自限定静态效果，以最低成本替代用户要比较的表现力。

**正例**：兑现获准候选的实现范围，按目标选择能区分方案的场景。发现退化后检查实现开销和负载代表性，明确哪些证据支持当前版本不宜采用、哪些问题仍未回答；若有效反证确实否定方向，也如实接受。效果优先时记录资源代价，不擅自将其设为否决门槛。

**落点**：实现问题、负载结果、方向适用性与采用建议需要不同证据。修正实验不是无限追加测试或坚持原方向；比较应回答原问题，范围调整仍须符合授权。

## 真正接入控件，不是仅做外观

**反例**：控件看起来像目标样式，却仍走旧事件路径；新增业务接口没有真实调用者；或直接调用业务方法成功，就声称鼠标／键盘操作已接通。用户问“能否换成某种控件”时直接迁移，也把讨论误当授权。

**正例**：比较阶段先解释目标控件会改变的输入、状态与维护责任，并给出推荐。获得实施授权后，从实际输入入口追到状态更新、业务副作用与用户可见结果，覆盖取消、失效及释放；迁移受影响调用者并去掉被替代的入口。选择、复制、删除等改变操作身份后，还要核对视觉选中、实际焦点、命令目标和下一次输入的交接，例如删除后能否立即撤销、复制后删除是否作用于新副本；不能只验证当前单次动作成功。

**落点**：设计检查负责确认完整接入与责任归属；交互验证由当前项目的真实输入和状态取证流程承担。外观、行为、资源收益分别需要相应证据，不能互相替代。

## 直接原因正确，不等于判断依据可靠

**反例**：定位到容器时间戳的起点／终点解释差异导致 FFT 窗口误重置，只修时间戳换算，并用原文件不再闪烁证明连续性模型正确。另一种反例是直接废弃时间戳、只累计帧数，消除误重置却掩盖真实媒体 gap 或分析丢样。

**正例**：利用不同可视化路径的差异，定位哪些消费者积累窗口、依据什么清空。随后分别明确媒体定位与样本连续性需求：样本及连续关系不变、仅合法时间戳表达改变，不应重置分析；时间戳看似平滑、实际丢样时，却不能跨接窗口。以这两个方向检验依据，再追查源边界、播放实际接纳与分析传输丢样各由谁确认、何时传播，防止提前解码的边界提前影响尚未接纳的音频。

**落点**：这是从现象、机制走向接口语义的推导示例，不是规定所有音频项目采用同一组字段或分层。若接口已可靠提供连续性事实，错误仅在某处换算，局部修正即可；确有重复猜测或语义混用才调整边界。事后能解释更好的方案，不证明当时已自主发现；用独立场景检验这条推导路径，不把原文件通过或模型解释练习当成完整验证。

## 计算去重不推迟权限边界

**反例**：完成回调与试听入口都校验来源，于是删除外层调用；只验证有效／失效来源都能正确接纳或拒绝，遗漏内层在校验前会恢复队列并写库。最终拒绝试听，不能撤销隔离状态下已经发生的写入。

**正例**：先拆出访问权限、来源有效性和恢复后权威状态各自的责任。把廉价权限检查保留在副作用之前，最终来源校验使用恢复后的状态，删除真正重复的查询与文件读取。检查禁止访问且存在待恢复选择时没有写入，正常与仅保留结果的路径仍按契约完成。

**落点**：同一 helper 的重复调用不证明责任重复，不同时点的检查也不天然都必要；按保护对象与生效时点判断，不为去重新增验证 token 或恢复完整重复计算。

## 接口退场不等于模型迁移完成

**反例**：搜索不到旧接口名，就宣称迁移干净；正常扫描已采用共享源与轻量引用，另一检查入口仍逐项复制旧记录。

**正例**：沿实际模型生产者、消费入口及必要夹具核对表达与所有权。保留检查入口只刷新已登记身份的独立行为，同时迁到统一模型；不通过删除该入口或复制新旧两套测试隐藏遗漏。

**落点**：符号搜索证明接口退场，不证明语义统一。按受影响的生产与消费链确认迁移，不因此扩成全仓审计或重跑无关验收。

## 新交错反例暴露的是同一个模型缺陷

**反例**：把“记录已确认不可用”和“正在查询／查询失败”放进同一互斥状态。重试覆盖不可用结论，旧保存成功回执又将状态恢复为可用。每发现一种回调顺序，就补一个枚举判断；已有测试通过，却仍有新的顺序绕过保存限制。

**正例**：先用反例确认业务事实与请求进度能够同时成立，再分清事件权限：重试只改变读取任务，读取失败保留已有可用性结论，保存回执只确认对应提交；读取结果仍需通过身份与版本检查才能更新业务事实。已有 owner 能完整承担时就在原处修正，不为此强建通用协调器或把所有状态拆成布尔值。

**落点**：用共同不变量解释不同顺序，再选择有区分力的确定性交错检查对外结果，例如重试失败后仍不能保存已确认不可用的记录、旧回执不使新查询失效。即使每次都有新证据，也不能把模型缺陷拆成无穷的个案补丁；这不意味着每个异步问题都需要重构、穷举或真实 GUI 验证。

## 等待超时不证明业务未提交

**反例**：导入请求发出后等待超时，界面直接标成“导入未执行”并自动重发；原请求稍后提交，造成重复导入。随后只增加一个超时判断，却仍把等待结果当作业务事实。

**正例**：先核对接口能否区分未接纳、明确拒绝、已提交和结果未知。有现成请求身份或状态查询时，用它确认原操作；不能确认时保留未知，不把超时解释成未提交。取消请求能否阻止提交、何时算执行结束，由业务 owner 的实际契约决定。

**落点**：先区分调用方观察与执行事实，不因此新建通用任务注册中心。纯读取、明确未接纳，或接口已保证幂等与安全重试的场景，可按各自契约处理，不把此例推广为禁止一切重试。
