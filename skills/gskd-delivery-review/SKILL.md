# 交付复查

## 触发与边界

适用于实现后的完整性复查、交付整理和提交前检查，不要求每项任务都走固定流水线。常驻 AGENTS 约束始终有效；本 Skill 不授予执行测试、提交或重写历史的额外权限，也不代表宿主具有自动派发或工具能力。

默认围绕本次交付和已有证据做必要核对，不为执行步骤而新增检查。仅提交已验收且未再改变的内容时，核对提交范围、改动归属和提交格式，不重启整轮验收，也不因准备提交而新增测试、文档或 GUI 巡检。发现新改动、旧证据失效或具体验收缺口时，只补受影响的检查；必要验收尚未完成时，不能借“仅提交”跳过。

本 Skill 负责确认既定要求是否闭合，不重新选择设计。探索交付沿用本次约定的深度：实验结论不能替代已授权的真实实现，也不把候选比较自动升级为正式接入或发布验收。只有具体发现推翻已接受的责任、状态或生命周期假设时，才进入针对性设计检查；只因收尾或提交不触发其他 Skill，目标与授权冲突则先解决该冲突。

## 步骤

1. **对照既定验收。** 直接复用当前任务的目标、授权、范围、不动项与验收，对应实现和证据；只有记录缺失、冲突或有后续修正时，才回查相关讨论补齐，不为收尾重做定向或另写契约。不能只看 diff，或把未接受的建议算作承诺；用户要求“整个讨论完整实现”时仍须覆盖全部有效要求。关键验收须有观察，未覆盖、已替代和证据失效项明确标出，不以测试数量代替。无需固定表格或逐项复述。
2. **确认归属。** 区分本次任务、用户和其他工作留下的改动；不因不在预期中就撤销、格式化、删除或纳入提交。仅为判断本次契约受影响而阅读关联改动；“别的不动”是范围限制，不是顺手整理的邀请。
3. **做有界闭合检查。** 围绕本次验收与受影响链路核对以下适用项，不按文件大小或改动数量扩大审计：
   - **行为闭合**：主路径与选定的失败、取消、交错场景兑现任务契约；结果属于当前身份与版本，不覆盖执行时的权威状态。
   - **责任闭合**：受影响调用方已迁移，状态提交、恢复与释放由明确 owner 承担，没有绕过必要转换的旧入口或可变 payload。
   - **成本闭合**：区分缺陷、可消除的浪费与为目标承担的成本；新增路径没有明显的重复失效／计算、无理由的全量刷新、临时复制、冷阻塞或无界工作。不以降低成本为由擅自牺牲目标，也不要求所有实验候选达到正式采用标准。删除重复工作不必先做基准；吞吐、延迟或内存收益须有对应证据，不因检查成本就引入新缓存或调度框架。
   - **结构与表达闭合**：核对责任、抽象和整体表达是否兑现已接受设计，没有靠冗余层、跨模块补偿或局部美化破坏整体。判断标准由 [design-review 的“抽象的判断”](../gskd-design-review/SKILL.md#抽象的判断)及[“表达与美学品味”](../gskd-design-review/SKILL.md#表达与美学品味)持有；仅在当前上下文不足以判断时补读对应小节，不重开方案比较。性能收益须有证据，清理不默认意味着删代码。
   修复本次引入或阻断既定要求的问题，修正后只复查受影响部分。明确获准的复查、修正和优化属于当前交付，应连续推进，不在首次运行成功或单轮测量后停下；优化不要求必须产生改动或测得收益，没有值得实施的改进时说明依据。已知验收缺口仍可验证或修正时继续推进；确有外部阻碍时说明缺口与影响。无关发现分开报告，不顺手实施；没有新证据就不重复全量审计或追加美化。
4. **整理测试与证据。** 保留能防止合理行为回归的边界、转换、错误和资源限制测试；删除失效、重复或仅锁定实现偶然值的测试，不能丢失独立行为覆盖。按风险分配证据：身份、revision、顺序、取消和资源边界可用确定性行为检查；查询、连接或计算次数的一次性取证用 throwaway smoke，不默认变成永久探针。输入、焦点、实际显示或平台行为的验收需要真实程序证据，按 GUI 验证 Skill 执行；不能用文件生成或属性返回代替界面显示成功，也不因涉及 UI 启动整轮巡检。区分已运行结果、静态判断和未验证项；复用未改变且仍适用的已有证据，改变的路径只补必要检查。
   GUI 取证按 [gskd-gui-verification](../gskd-gui-verification/SKILL.md) 的触发条件与执行方法，只补本次证据缺口；已有适用证据不因补读技能而失效。
   跨版本、跨环境比较或需要长期引用的重要运行证据，应保留足以定位源码及未提交改动、构建配置、实际产物和运行对象的信息；可覆盖的路径、包版本或笼统的 dirty 标记不能单独作为唯一身份。记录深度以能判断证据适用范围为准，不强制每次保存完整差异、产物副本或哈希。版本或环境改变时先判断哪些证据失效，不一律重跑，也不直接继承。
5. **同步文档与交付。** 只在有意义的行为、契约或设计变化时更新权威文档，按入口、用户参考、技术设计分层，不重复写流水账。获准提交时按责任拆分，保留他人改动，遵循仓库提交格式；重写已有历史（含 amend、rebase 或重排提交）须另有明确授权。

后续发现问题时先区分：契约遗漏、明显浪费、实测瓶颈、视觉／使用反馈。前两类若反复出现，补其对应阶段的通用检查方法；瓶颈按实际工作负载取证，视觉反馈正常迭代，不都归为首次交付失败。不得把单个项目特例堆成常驻规则、以提交数量衡量质量，或借归类获得额外修改授权。

按疑问补读 [取舍与案例](references/review-decisions.md)：测试去留看“测试”，文档分层看“文档”，授权范围看“讨论完整性与范围”，承诺场景缺证看“验收”，探索交付深度看“实验交付”，提交归属看“提交”。不必通读无关小节；项目案例不是跨项目默认需求。

## 产出与停止

- 简要交付：已接受要求的落实情况、实际检查及结果、仍缺失的证据或外部阻碍；实验注明结论的适用范围、剩余成本取舍及与正式采用的区别，有提交时说明责任边界与必要依赖。
- 目标问题已有有效证据，约定的候选、复查与优化等验收项有落实或经用户明确同意调整，必要文档与测试已处理，剩余取舍和证据边界已说明后停止；不因候选未获采用就否定实验价值，也不为“再完善一点”制造新工作。
- 仍有可执行的已接受事项就继续，不用“后续再做”替代完整交付。权限、环境或信息确实缺失时，完成可达部分，明确阻碍及其影响，不宣称全部完成。
