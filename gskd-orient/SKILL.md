# 任务定向与续接

## 触发与边界

用户提出任务，或对正在进行的任务提问、补充、纠正、改范围、调优先级、暂停或恢复时使用。它整理意图、执行边界与必要的实现契约，不取代 AGENTS 的常驻底线，也不赋予额外工具、任务队列或后台执行能力。

## 接入判断与按需处理

先判断对象和授权，再按本次消息涉及的情境处理后续事项、实现契约或暂停恢复；这些是按需检查，不要求每次完整走一遍，也不要求逐项向用户复述。

### 1. 绑定对象，再判断消息作用

先读当前请求、直接相关的前文和已有任务记录，确定对象、版本、范围与否定限制；不要仅凭最后一句或熟悉的原因猜测。

| 表达 | 绑定方式 |
| --- | --- |
| “1 按建议执行” | 对齐前文的编号项及该项建议；“1”不是授权执行所有建议。 |
| “别的不动” | 与同句的正向授权一起生效；未授权的相邻优化和清理留在范围外。 |
| “前面发现的问题” | 回查所指发现列表及尚未解决项，不偷换成最近一个问题或重新全面审计。 |
| “整个讨论方案” | 汇总讨论中仍有效的决定、依赖和验收，不只执行最后一项；排除已撤回或被替代的方案。 |

一条消息可同时有多种作用：
- **提问**：回答其问题，不默认撤销已有任务，也不默认取得修改授权。
- **补充**：将新约束并入当前对象；只有明确替代才删除旧约束。
- **纠正**：先更新对象、现象或约束，撤下不再适用的假设与行动。用户报告的新观察是事实；原因仍待定位，不拿旧原因否定新观察。
- **新任务**：区分独立交付与当前任务的必要步骤，不自动挤掉当前工作。
- **优先级变化**：调整先后顺序；“先做 A”不等于取消 B，也不自动扩大 A 的范围。

### 2. 判定授权，主动推进

分别确定本次获准的是**回答**、**调查**还是**实施**；它们可以组合，但讨论建议不等于批准改动。明确的“执行”“修复”“按这个方案做”结合已绑定范围即构成实施授权，不再反复索要确认。

可从上下文、仓库或可用工具消除的疑问自行解决。只有歧义会实质改变对象、范围、不可逆影响或验收，而且现有信息无法消除时，才问最小必要问题；不受该歧义影响的已授权工作继续推进，不把所有疑问都变成阻塞。

### 3. 分开当前交付与后续事项

确定现在必须完成的结果、保留不动的部分、完成条件，以及之后才讨论或执行的事项。“继续检查、清理完再讨论”先完成已授权的检查与清理，不提前用讨论替代交付；也不借“检查”扩成新的全面整治。

宿主确有任务记录或队列能力时，复用其真实接口和状态语义；没有时只在当前对话简记后续事项及恢复条件，明确这不是已入队或将自动执行。未完成、等待讨论、暂停都不能伪标为 `completed` 或 `abandoned`；记录后续事项不等于授权执行，不承诺后台监听、自动派发或跨会话自动恢复。

### 4. 把实现风险转成验收项

对已授权且涉及状态、异步或资源的改动，先读相关实现与约定，在首次生产修改前于当前任务记录或对话中简记关键不变量和对应验收；已有明确契约直接引用，不重复复述。读取本 Skill 或相关代码本身不代替契约简记；未知原因仍标为待查，不用猜测补齐。无需新建设计文档、固定表格或为每个字段增加任务：

- **目标与权威**：消费者最终得到什么；哪个 owner 决定最终状态，请求携带身份、增量还是快照，排队后执行时需要重读什么。仅修改部分状态时，传目标变更或由 owner 合并，不能用旧快照覆盖未编辑字段；确需版本快照时明确冲突处理。
- **转换与有效性**：区分业务事实、操作进度与操作意图；可同时成立、独立变化的状态不能相互覆盖。明确开始、完成、失败、取消各自有权修改什么、必须保留什么，以及目标、版本或窗口改变后允许结果提交的条件。按当前问题记录必要约束，不预设枚举、token 的数量或固定状态机结构。
- **成本与边界**：哪里有 I/O、分配、复制或阻塞；哪些容量和单轮工作需要有界，受影响消费者有哪些。
- **验收与不动项**：把主路径和最有风险的交错写成可观察结果，同时保留已确定的范围限制。按风险选择目标改变、取消与完成交错、失败后重试、未知与空结果、隐藏／重开、无关修改等场景，不要求全套矩阵。

后续要求或新证据改变目标、状态权限、结果有效性或资源边界时，只更新受影响的契约与验收；普通实现细节调整不要求重写。原因未明时保留待查项，不将假设写成已接受事实；改变已接受要求仍须取得用户接受。

简单样式或机械修改只明确目标、必要验收与不动项；提问不启动实施流程。现有边界清楚就直接实现；有实质取舍或责任疑点时，按 [gskd-design-review 的“触发与边界”](../gskd-design-review/SKILL.md#触发与边界) 进入针对该疑问的设计检查，实施授权本身不要求完整设计评审。

初步查明范围与依赖后，主动评估已授权的独立事项能否由子代理并行推进；按责任与依赖判断独立性，收益应抵过交接和整合成本，小改动不机械拆分。委派前明确共享契约、各项范围与验收，由主代理整合并确认整体完成；具体调度遵循宿主规则。

### 5. 暂停、讨论与恢复

用户要求暂停时，在安全停点停止新的实施操作，保留已做改动，记住当前对象、已完成/未完成部分和停止位置；不擅自回滚。若确有运行中的任务，按宿主能力处理并说明真实状态，不把“要求停止”说成“已经停止”。

讨论期间按问题回答或在授权内调查；只有新的明确授权才改变实施范围。用户说“继续”时，绑定暂停的任务，合并讨论中已确认的变化，检查当前状态后从未完成处恢复；仍未决的方案不混入实施。若仅有“做完再讨论”的顺序要求，则先交付当前任务，再进入已约定的讨论，而不是中途暂停。

## 产出与停止

复杂续接或范围变化时，用简短说明交代：**本次对象与授权、当前交付与不动项、后续事项及恢复条件**；范围清楚的简单请求直接行动，不固定输出一套表格。

当前授权结果满足完成条件才结束执行；只回答的问题答清即可停止。遇到明确暂停、需用户决定的关键歧义或不可达前置条件时，保留实际状态并准确说明停点，不宣称任务完成。当前交付完成不代表后续事项获准实施。

需要对照易误判情境时，按 [历史场景与用法](references/examples.md) 的对应小节补读：交付与讨论顺序看“Layout：先交付，再讨论”，编号授权与不动项看“72M”，新观察与旧解释冲突看“组件”，整体方案、暂停或优先级切换看“通用续接示例”。不必通读无关案例；案例是历史归纳，不是项目永久规则或本次验证证据。
